# Athena Agent Program

This document is for agents proposing changes to Athena-managed research, not for running a local orchestration loop.

Athena is Kubernetes-native. Agents may propose desired state by editing or creating Kubernetes custom resources, runner code, or controller code. Controllers own observed state, lifecycle transitions, metric parsing, benchmark comparisons, events, and status.

## Source Of Truth

- Create or update `Experiment`, `BenchmarkSuite`, `BenchmarkRun`, `MetricSource`, `ResearchCampaign`, and `RuntimeProfile` specs.
- Do not write authoritative `status` from client code, scripts, console endpoints, or agent workflows.
- Do not record experiment outcomes in local files, SQLite, local KV stores, logs, or ad-hoc REST services.
- Do not use local GPU acquisition or worker pools. Kubernetes scheduling, resource requests, node labels, and `RuntimeProfile` policy own execution placement.
- Do not make promotion or revert decisions from client-side log parsing. Controllers derive outcomes from declared artifacts, Job/Pod status, benchmark gates, and status conditions.

## Research Workflow

1. Inspect existing CRDs, examples, and `docs/openspec.md`.
2. Define desired research intent as Kubernetes resources:
   - `ResearchCampaign` for autonomous loop policy and aggregate outcomes.
   - `ExperimentTemplate` or `Experiment` for concrete trial shape.
   - `BenchmarkSuite` for benchmark tasks, metrics, budgets, gates, and integrity policy.
   - `MetricSource` for declared artifact parsing.
   - `RuntimeProfile` for runner image, resources, GPU scheduling, workspace, and sandbox policy.
3. Change workload code under `experiments/` only as stateless runner implementation.
4. Ensure workloads emit structured metric artifacts with stable lowercase snake_case keys.
5. Let the Athena operator reconcile Jobs, parse metrics, update status, emit Events, and expose Prometheus metrics.
6. Inspect results through `kubectl`, Athena Console, Prometheus, Grafana, and CR status.

## Workload Code Rules

- `experiments/prepare.py` and `experiments/train.py` are workload implementation details for Kubernetes-managed Jobs.
- Workload code must not own scheduling, durable state, campaign policy, benchmark comparison, promotion decisions, or authoritative status.
- Local runs are smoke tests only. They must not be used as the source of truth for `Experiment`, `BenchmarkRun`, `ResearchCampaign`, or metrics status.
- Metrics must be written as declared JSON/JSONL artifacts. Stdout may mirror metrics for debugging, but logs are not authoritative.
- Workspace paths, data paths, output paths, seeds, budgets, and target refs should be injected from Job environment/config generated by the controller.

## Status And Metrics Rules

- Controllers derive status from Kubernetes Job/Pod state, declared artifacts, controller-observed timestamps, and validated refs.
- Status conditions must represent lifecycle transitions, parse failures, budget exhaustion, integrity failures, retries, terminal success, and terminal failure.
- Runtime/cost metrics such as `wall_clock_seconds`, `queue_latency_seconds`, and `gpu_hours` come from controller-observed state.
- Raw item-level results stay in workspace artifacts; CR status stores bounded summaries, refs, hashes, and conditions.

## What Not To Do

- Do not call legacy local REST endpoints to register, complete, or crash experiments.
- Do not run indefinite local loops that mutate git based on local metrics.
- Do not parse logs to infer benchmark success.
- Do not extend `workers/orchestrator/` or `workers/gpu/` for Athena features.
- Do not use local files or local databases as product state.
